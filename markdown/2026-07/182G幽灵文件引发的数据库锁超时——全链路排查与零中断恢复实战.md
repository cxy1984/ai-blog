# 182G 幽灵文件引发的数据库锁超时 —— 全链路排查与零中断恢复实战

> **一句话梗概：** MySQL 报 `Lock wait timeout`，根因却是 182G 已删除的日志文件被进程"卡住"未释放，导致磁盘写满、binlog 阻塞、事务全部排队。本文完整复盘从数据库报错→系统层定位→零中断恢复的全过程，并深入拆解每一个技术决策。

---

## 一、现象：一条 DDL 引发的血案

测试环境，同事在修改配置表 `configure` 时，突然抛出异常：

```
Error 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

**关键区分：** 这不是 `Deadlock found`（死锁），而是 `Lock wait timeout`（锁等待超时）。说明有事务持有了锁一直不释放，后续事务等待超过了 `innodb_lock_wait_timeout` 默认的 50 秒阈值。

---

## 二、排查第 1 层：数据库内部探查受阻

### 2.1 `SHOW PROCESSLIST`

查看当前连接状态，发现大量连接堆积，但**Processlist 只能看到"谁在执行"，看不到"谁持有了锁"**。更关键的是，stat 列暴露出大量 **`Writing to binlog`**——这是磁盘 I/O 卡住的信号。

### 2.2 `SHOW ENGINE INNODB STATUS`

为了看清锁的持有关系，继续执行 InnoDB 监控。重点关注 **LOG** 部分的三个序列号：

```
Log sequence number     12227732543514   ← 内存中已写入的 LSN
Log flushed up to       12227732542000   ← 已刷到磁盘的 LSN
Pages flushed up to     12227732540000   ← 脏页已刷盘的 LSN
```

> **解读：** `Log sequence number` 远大于 `Log flushed up to`，说明内存里的 redo log 积压严重，刷盘线程跟不上。`Pages flushed up to` 更是大幅落后，磁盘显然没有正常写入。

**至此，数据库层面的排查给出两个关键暗示：**
1. 有大量事务在等待 binlog 写入
2. InnoDB 的 redo log 也无法正常刷盘

两者都指向同一个方向——**磁盘出了问题**。

---

## 三、排查第 2 层：错误日志一击命中

转向 MySQL 错误日志（MySQL 5 需到服务器本地查看），`tail -f mysql_error.log`：

```
2025-10-20T09:24:04.476735Z 8660137 [ERROR] 
Disk is full writing './mysql-bin.000972' 
(Errcode: 15410240 - No space left on device). 
Waiting for someone to free space...
```

> **真相大白：** 不是锁竞争，是 **磁盘满了，binlog 写不进去**。MySQL 在事务提交时必须写 binlog，写不进去事务就挂住，锁也就一直不释放，后续事务全部排队等超时。

这是典型的**表象与根因分离**案例：业务报错是锁超时，根因是磁盘满。如果只盯着锁分析，大概率会走弯路。

---

## 四、排查第 3 层：`df` 与 `du` 的 192G 鸿沟

### 4.1 确认磁盘使用率

```bash
df -h
```

`/Z_Datas` 分区 300G，利用率 **100%**，已用 298G。

### 4.2 逐层统计却对不上

```bash
du -h --max-depth=1 /Z_Datas
```

所有子目录加起来 **仅 ~106G**。已用 298G 却只找到 106G，**差值高达 192G**。

### 4.3 三种可能性排查

| 可能性 | 分析 | 结论 |
|--------|------|------|
| 隐藏文件 | `du` 默认可见 `.` 文件，不可能有 192G 这么大 | ❌ 排除 |
| 独立挂载点 | 确认所有子目录在同一分区 | ❌ 排除 |
| **已删除但仍被进程占用的文件** | `rm` 只删除目录项，若进程仍持有 fd，内核不释放 inode | ✅ **定位** |

> **黄金信号：** `df`（文件系统级）和 `du`（目录遍历级）的数值差异，是诊断"幽灵文件"的经典标志。

## 五、排查第 4 层：`lsof` 捕获真凶

```bash
lsof | grep deleted | grep /Z_Datas
```

输出直击要害：

```
/Z_Datas/pqcModel/logs/logs.txt (deleted)   182.5G   PID 4624
/Z_Datas/dpxz/logs.txt (deleted)             23.7G   PID 4990
```

**PID 4624** 持有已被删除的 `logs.txt`，**182.5 GB** 空间就这么被"卡住"了。进程 4990 类似，23.7G。

### 场景还原

服务启动时将 stdout/stderr 重定向到 `/Z_Datas/pqcModel/logs/logs.txt`。后来运维做日志清理，执行了 `rm`，但**服务没有重启，也没有收到信号重新打开日志文件**。进程继续往原文件描述符写入，数据在 inode 层面不断累积，但目录项已被删除，文件在文件系统上"不可见"。

### 完整根因链

```
服务日志未正确轮转 
  → 日志文件被 rm 但进程未释放 fd 
    → 182G 空间泄漏 
      → /Z_Datas 分区写满 
        → MySQL binlog 无法写入 
          → 事务提交卡住 
            → 锁无法释放 
              → 其他事务 Lock wait timeout → Error 1205
```

## 六、解决方案：三选一的工程决策

| 方案 | 操作 | 优点 | 风险 |
|------|------|------|------|
| A. 重启服务 | `systemctl restart <service>` | 简单直接，fd 关闭即释放 | 未知服务用途，重启可能影响其他同事 |
| B. `kill -HUP` | 发送 SIGHUP 信号 | 优雅重载日志 | 不确定服务是否实现了信号处理逻辑 |
| C. **清空 fd 内容** | 操作 procfs 直接截断文件 | **零中断、低侵入、可逆** | 需要足够权限 |

**决策：** 测试环境也要有生产意识——**选择 C，不中断服务的前提下释放空间。**

## 七、执行攻坚：权限问题的巧妙绕过

### 首次尝试：重定向失败

```bash
> /proc/4624/fd/1    # 清空 stdout
> /proc/4624/fd/2    # 清空 stderr
# Permission denied
```

**原因：** `/proc/PID/fd/N` 是一个软链接，指向已删除文件的 inode。`>` 重定向会以当前用户身份去打开底层 inode，如果进程 4624 以其他用户运行，权限检查就会拒绝。

### 二次尝试：`dd` 命令成功

```bash
dd if=/dev/null of=/proc/4624/fd/1
```

输出：
```
0+0 records in
0+0 records out
0 bytes (0 B) copied
```

### `dd` 为什么能绕过权限？

关键在于 **procfs 的特殊机制**：`/proc/PID/fd/N` 路径在 procfs 中允许通过进程的 fd 表直接写入，而不需要重新打开底层文件。`dd` 直接操作这个 procfs 入口，绕过了传统文件权限的层层检查。`/dev/null` 提供 0 字节输入，写入 fd 1 的效果等同于**将文件内容截断到 0**。

### 操作完成后立即验证

```bash
# 对 PID 4990 重复操作，释放 23.7G
dd if=/dev/null of=/proc/4990/fd/1

# 验证磁盘
df -h                    # /Z_Datas 从 100% 降到正常
# 验证 MySQL
# 同事重新执行操作，Error 1205 消失，事务正常提交
```

## 八、技术深度：为什么 `rm` 不等于真正的删除？

这是理解本次事故的关键知识点：

```
文件在磁盘上的生命周期 = 目录项存在 && link count > 0 && 无进程持有 fd
                                   ↓
                  rm 只移除目录项，link count 减 1
                                   ↓
                link count > 0 → 文件仍然存在（硬链接）
                link count = 0 && 仍有进程持有 fd → inode 和数据块保留
                link count = 0 && 无进程持有 fd → 真正释放
```

> **核心教训：** `rm` 只是 `unlink`，真正的文件释放需要**链接计数归零且没有进程打开文件描述符**。容器化环境、日志服务中"边删边写"的场景极为常见。

## 九、事后复盘与工程启示

### 9.1 全栈思维

数据库报错，根因可能在操作系统层面。`SHOW ENGINE INNODB STATUS` 权限不足反而"逼"我从系统日志切入，结果更快定位了问题。**技术栈的每一层都不是孤岛。**

### 9.2 排查方法论

| 步骤 | 工具/命令 | 目标 |
|------|-----------|------|
| 数据库连接状态 | `SHOW PROCESSLIST` | 发现 `Writing to binlog` 异常 |
| InnoDB 引擎状态 | `SHOW ENGINE INNODB STATUS` | 发现 redo log 刷盘阻塞 |
| MySQL 错误日志 | `tail -f mysql_error.log` | 直击 `Disk is full` 根因 |
| 磁盘使用率 | `df -h` | 确认分区 100% |
| 目录空间统计 | `du -h --max-depth=1` | 发现 192G 差额 |
| 已删除文件 fd | `lsof \| grep deleted` | 定位幽灵进程与文件 |

### 9.3 工程决策原则

**低侵入、可逆的操作优先** —— 在信息不完整时，不贸然重启未知服务，而选择 `dd` 清空 fd 这种零中断方式。

### 9.4 推动规范落地

排查结束后，推动团队落实了以下措施：

1. **日志轮转规范：** 使用 `logrotate` 的 `copytruncate` 模式，或确保服务支持 `kill -HUP` 重载日志
2. **磁盘监控告警：** 80% 阈值预警，杜绝等 100% 才被动处理
3. **应用层日志库热切换：** Python 的 `WatchedFileHandler`、Java 的 `logback` 热配置等
